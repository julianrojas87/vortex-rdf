Three cargo bench targets: benchmark.rs (the instrumented internals suite), match_lazy.rs (the same matrix without materialization), and compare.rs (the cross-library comparison). The internals suite is one-factor-at-a-time over three axes — column layout, secondary index, and source — each crossed with the cold/warm cache regime. Each panel isolates one axis against a fixed baseline; the raw table holds every measured configuration. All three run the same dataset shape (—), so a pattern's row count means the same thing wherever it appears.

BUILD

Build & open

This store against RDF library alternatives in Rust. Every entrant ingests the same N-Triples file at the same scale (— rows), one library per process. The Vortex-internal panels further down generate the same quads in process instead of parsing them from a file — that suite is uploaded to CodSpeed, where a multi-hundred-MB read inside a measured region would swamp the instruction counts — so a pattern matches the same quads in both halves of this tab, and matching file variants agree between them. Two build differences to know when crossing: files here come from the streaming writer while the internals suite serializes an already-built store (the two artifacts differ ~2× on warm file points), and the in-memory rows here reopen through the serialized parts, as the bindings do — so their cold cells price the first query on a freshly adopted store: first-touch probe setup over the file writer's compressed chunks, where the internals' built stores hold canonical columns. Measured 4–8×, and isolated to the arrays' encodings — the parts round-trip itself is free, and both bases are chunked alike. oxigraph enters twice — its in-memory store and its RocksDB-backed one, the same library across the residency axis the Vortex (file, memory) pairs cross; sophia holds its data in memory; hdt is the closest thing here to a peer — a compressed, read-only RDF file format, and the other entrant with a persisted artifact to open.

QUERY

Match — cross-library

Resolving each pattern and counting the results: S/P/O/PO/SPO/full on triples. Every library counts by iterating what it returns; Vortex materializes four terms per row, which on a triple pattern is strictly more work than the libraries returning triples. G/SPOG run on the shared named-graph dataset (— quads); hdt has no quads at all, so its cells there read unsupported.

MUTATE

Add & delete

Per-quad addition into an empty store and per-quad deletion from the full store (reopened or rebuilt per iteration, untimed), batch of —. Vortex checks presence on every add (set semantics) and tombstones deletes; its add_quads batch column is the recommended path — the per-quad loop rebuilds the tail each call by design. One Vortex row: mutation starts from an empty store, which no layout or index knob reaches. hdt is immutable once built.

FOOTPRINT

Peak memory & on-disk size

Each library runs in its own process, so peak RSS is the kernel-tracked high-water mark (VmHWM) for one library alone — build, open and every pattern in that process. On-disk size is the artifact the build produced; it reads unsupported for a library that keeps its store in memory. Lower is better in both tables.

Vortex internals

Everything below measures Vortex against itself, on the same dataset shape as the cross-library file above (—) — generated in process rather than parsed, since this suite is the one CodSpeed instruments. QUERY

Match — pattern resolution

Vortex against itself — the cross-library table above answers “how does this store compare”, this one answers “which of its knobs moved the number”. Same materializing measurement, same probes over the same term shape, but a Vortex-only variant set (18 cells: layout × source × index, plus the Bytes adoption rows). Resolving match_pattern and materializing the matching quads, across the six routing shapes the resolver branches on: S (primary binary search, —), P/O (single-column index probe, —), PO (two-column prefix probe, —), G (no index covers graph — mask scan, —), and SPOG (every component bound, —). S, P, O and PO match the same rows the cross-library table's do; G does not — the shared named-graph file is a separate, half-size dataset. Matching file variants agree with that table's; the deliberate exception is cold in-memory, where that table reopens through the serialized parts (adoption, what the bindings hand out) while these stores are built in place — its first query resolves probes over the file writer's compressed chunks, these over canonical columns; the difference is the encodings, not the adoption machinery.

DICT

Dictionary — residency

The Dictionary layout's term dictionary rides inside the quads file as an embedded metadata-segment blob (one self-contained file; the quad columns stay bare). Residency: the blob is lifted into memory at open (resident) or left in the file and reached by pruned scans through a bounded reader (file-backed) — decided by the blob's byte size. One npm run bench run of js/bench/compare.bench.ts — the VortexRdfStore WASM bindings compared against rdf-stores.js, oxigraph-js and hdt (the Rust crate's read-only wasm bindings over a natively pre-built artifact — its ingest, named-graph and mutation cells read unsupported by construction), on a synthetic dataset whose distinct term count scales with the rows (each subject described by about ten triples, a small closed predicate vocabulary, a mix of IRI and literal objects), across build, open, query in both cache regimes, full scan, add and delete. Wall-clock (tinybench) — deliberately not uploaded to CodSpeed.

Term cardinality matters because it is what exercises each library's dictionary and string handling; selectivity follows the data, so each pattern's matched-row count is recorded in config.matchedRows alongside its timing.

BUILD

Build & open

Build is each library's idiomatic bulk path from the generated triples to a queryable store (Vortex fromQuads, oxigraph new Store(quads), rdf-stores per-quad addQuad) — apples-to-oranges by construction, so read it as “time to a queryable store”. Open is what a fresh process pays to query a store someone else already built; only the stores with a persistent form have one.

QUERY

Match — cross-library

Resolving match and counting results across routing shapes: S/P/O/PO/SPO/full on triples, G/SPOG on named graphs. Counting consumes: every result term's value is read. Vortex terms are lazy wasm-backed values that cross the boundary on read, while the pure-JS stores hold eager objects — reading them all makes materialization part of the measured work here, exactly as on the Rust and Python tabs, and puts the wasm boundary cost on the page instead of hiding it.

MUTATE

Add & delete

Incremental per-quad additions and deletions of a fixed batch. Vortex routes these through its tail/tombstone model, so per-quad addQuad trails the recommended addQuads batch path — both are shown.

FOOTPRINT

Peak resident-set size per adapter, the kernel-tracked high-water mark (VmHWM), not a point-in-time sample. Lower is better.

One python/bench/run.py run — the vortex_rdf bindings compared against pyoxigraph, pycottas, rdflib, and lightrdf, on the same generated dataset the JavaScript tab uses (identical moduli, identical term spellings) — and the very same file the Rust tab's cross-library comparison reads — so rows on all three tabs describe the same data.

The shape of this comparison differs from the JavaScript one, because the libraries do. Every one of them ingests from a file, so the workload is file → store → query rather than array → store → query, and Open is a first-class column: what a fresh process pays to query an artifact someone else already built. Only the libraries that write one have a cell — for a store that lives in memory, opening is re-parsing the source, which is the Build column. Two libraries are read-only and one is not a store at all — those cells read unsupported, which records an absent API, not a slow result.

Vortex appears once per build configuration rather than as a single row, because its knobs — column layout, secondary index, and whether the store is read from the file or loaded up front — move these numbers as much as the choice of library does. Residency is crossed with the secondary index, so each (file, memory) pair shares a build: the difference between the two is residency alone, and it can be read with an index and without one. The in-memory indexed rows are the configurations that match how pyoxigraph and rdflib hold their data.

BUILD

Build & open

Build is each library's idiomatic path from an N-Triples file to a queryable store (serialize_rdf, bulk_load, rdf2cottas, Graph.parse). Open is what a fresh process pays to query an already-built artifact. pyoxigraph and rdflib hold their store in memory and have no artifact to open — a fresh process re-parses the source, and that cost is already the Build column, so those cells read unsupported rather than repeating it against a footer read. lightrdf builds nothing; its “build” is one full parse, the same pass every other library must do before it can index anything.

QUERY

Match — cross-library

Resolving each pattern and counting results: S/P/O/PO/SPO/full on triples, G/SPOG on named graphs. Counting is the only unit all five share, and each library materializes its own natural result form — Vortex builds N-Triples strings in Rust, pyoxigraph and rdflib yield term objects, pycottas and lightrdf yield tuples of strings. Residency differs too: the Vortex (file) rows and pycottas read from disk per query, while the Vortex (memory) rows, pyoxigraph and rdflib answer from memory. lightrdf is the no-index baseline: it has no store, so every pattern re-parses the whole source file and costs about the same regardless of selectivity.

MUTATE

Add & delete

Per-quad addition and deletion of a fixed batch. Only two of the five libraries can do this at all: the Vortex Python bindings expose no mutation API (unlike the JS bindings, which have addQuad/addQuads), pycottas's store raises “The COTTAS store is read only!”, and lightrdf is a parser with no store to mutate. Hover an unsupported cell for the reason.

FOOTPRINT

Peak memory & on-disk size

Each adapter runs in its own process and its own virtualenv, so peak RSS is the kernel-tracked high-water mark (VmHWM) for one library alone. On-disk size is the artifact the build produced; it reads unsupported for a library that keeps its store in memory and writes no file of its own, and for lightrdf it is the source N-Triples file it re-reads. Lower is better in both tables.
